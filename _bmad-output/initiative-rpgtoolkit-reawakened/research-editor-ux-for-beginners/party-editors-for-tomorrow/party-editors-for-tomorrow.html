01 · From a drawing to a vocabulary

“I want to build a village.”

Begin in Assets, not on a board. Make Village Houses, then draw or import one house on a sheet. Tile boundaries remain visible without interrupting the drawing.

Repeat the appropriate middle pieces. Don’t stretch the whole image or promise arbitrary resizing.

Properties / Village Houses
Reuse asFixed Stamp or resizable parts
Author the resizable brushPick left end · middle · right end
Entrance destinationOwned by this placed house
Edit scopeShared source / Make unique here
  1. Place it once. Save the whole drawing as a fixed Stamp. Useful immediately, without configuring a kit.
  2. Teach it to repeat. Optionally assign wall and roof parts visually, then test supported widths. Draw missing pieces instead of expecting the editor to invent them.
  3. Make it a functioning house. Add visible wall/walk-behind regions using tiles or vertices, then an entrance with its own destination.
  4. Reuse safely. A Component can group art, shapes and the entrance. Recolour one roof through an explicit unique copy; shared edits preview all affected uses.

🎨 Sally: Give me something useful before you ask me to classify every piece.

💻 Amelia: But get to flexible parts quickly, or a village becomes twelve identical cottages.

What is still a proposal?

Resizable brushes, linked Components, instance parameters and shape adjustment need data contracts. A Stamp is visual placement, not a substitute that silently drops behaviour. Multi-floor canopy semantics remain open.

02 · Beautiful is not the same as walkable

“I want a forest maze.”

Create the Forest kit: floor, path, trees and undergrowth. Make a terrain brush by assigning source artwork to the labelled edges and corners a sample path needs.

Canopy can overhang a passage. The trunk footprint—not the whole green picture—may block movement.

Properties / Path brush
Visual materialsPath ↔ Forest floor
Missing corner?Highlight the required source slot
OverlayEffective blocking + player footprint
VerifyWalk from entrance to exit
  1. Paint the route. Fill the floor, mark entrance/exit, and sketch paths and dead ends. Terrain rules repair visual joins.
  2. Build the forest around it. Place tree assemblies or paint forest walls. Inspect blocking and walk-behind assignments; do not infer either from pixel colour.
  3. Try a tight bend. The path may look clear while a trunk or explicit vector still blocks the player. Keep those shapes visible; a tile override must not silently erase a Wall.
  4. Reuse the kit elsewhere. Board layouts stay separate while shared art definitions remain reusable. Portable packs must preserve dependencies and editable source, not just a PNG.

📋 John: A lovely maze that nobody can finish still fails the task.

🏗️ Winston: A route checker must use effective collision and the actor’s footprint. A flood-fill of brown pixels is not proof.

What is still a proposal?

Terrain rule storage, reusable collision metadata, pack formats and route checking remain open. Painting paths first is one teaching sequence, not a decision against filling blocked forest and carving routes.

03 · Connect tasks without losing the author

“Talk to this person. Then fight.”

Place Forest Bandit from Things → Person. Start the interaction in the right-side Properties, without sending the beginner off to configure random encounters.

Forest / Forest Bandit / Interaction
WhenThe player interacts
Say“Nobody passes without facing me.”
ThenStart battle against Bandit
After victoryStay and talk / Disappear / Move aside / Custom
  1. Choose or create the Enemy. Keep a breadcrumb back to this interaction. Creating the enemy returns with it selected.
  2. Use the selected battle system. Show the fields and any specialist editor it actually requires. A walking Person and combat Enemy are distinct definitions.
  3. Choose the return state. “Until defeated” means confirmed victory, not “the first time the trigger ran.” Escape does not consume the challenge.
  4. Test the chain. Approach → dialogue → battle → returned board → interact again. An enemy-only preview misses the hand-offs.

💻 Amelia: This is helping you author ordinary RPGCode, not inventing a separate limited way to make games.

🏗️ Winston: Only if the script can call the necessary capabilities. Generating code doesn’t settle how battle outcomes resume the interaction.

The important unresolved boundary

Battle result/continuation ordering, plugin-owned effects, rewards and persistent-state updates need an explicit contract. This walkthrough does not claim that fightenemy returns a Boolean or supply an invented RPGCode signature.

04 · Now try to break the happy path

A watching trainer beside dangerous grass.

Give Scout a four-tile forward sight lane. Add Notice → Approach → Speak → Battle. Place a sight-blocking boulder and an encounter-grass region nearby.

Approach from behind

No sight activation. Talking can be an additional explicitly enabled activation.

Cross behind the boulder

No notice while occluded. Mark sight blockers deliberately; walking walls are not automatically visibility walls.

Obstruct the approach

Choose a visible blocked-route policy. Stop and wait is this example’s proposal—not teleporting or retrying forever.

Escape and return

Scout remains unbeaten. Proposed re-arm: leave and re-enter sight, rather than instantly starting another battle on return.

Win, leave, reload

Stay and talk uses the later line. Disappear removes picture, collision and activation persistently.

Grass and Scout trigger together

Candidate default: the scripted challenger wins; no surprise random battle queues behind it. An already active encounter is not interrupted.

🎨 Sally: The author should arrange a watching trainer beside dangerous grass, not debug two unrelated event systems.

🏗️ Winston: Two watchers, active battles and held input still need deterministic ownership and re-arm rules.

Questions the preset must not hide from its implementers

Sight geometry, layers, occlusion, approach failure, encounter overlap, counter reset/advancement and arbitration are unresolved. The author should not need to configure all of them, but the implementation cannot leave them unspecified.

05 · A small vocabulary that can grow

“Those snippets could be templated.”

The owner’s direction: common interactions generate RPGCode files, with templates somewhere easy to extend. A friendly interface does the repetitive authoring without taking away the language.

Add behaviour / Locked chest
Declared inputRequired key
Declared inputContents and messages
Supporting stateFresh opened state for this placement
OutputProject-owned RPGCode · Open program
  1. Find a pattern. Search Built-in, This project or My library.
  2. Fill its declared inputs. The template describes the controls; the editor doesn’t guess forms from arbitrary code.
  3. Keep the result. Programs remain organised and reachable from their board Things.
  4. Customise deliberately. Hand editing must follow explicit source ownership. A template update cannot silently overwrite your changes.

📋 John: Sharing a useful behaviour shouldn’t require becoming an editor-plugin developer.

💻 Amelia: Insert a useful starting point—not a permanent dependency that can rewrite your game behind your back.

Direction versus mechanism

Templates and accessible RPGCode are the direction. Input schema, packaging, folder spelling, generation ownership and library-update mechanics are proposals. Shared state is opt-in; independent placements must not accidentally share literal variable names.

06 · The last exercise before lights out

One chest. Then two.

Make a locked chest, save it as a behaviour template, and give the template to the next beginner. This tests whether our convenience survives reuse.

  1. Configure the first chest. Requires Old Key; keeps the key. Locked message, contents, empty response and open appearance are visible choices.
  2. Test each state. No key, correct key, already opened, leave/return and reload. Opening must not grant the contents twice.
  3. Save as template. Expose key, contents and messages. Allocate fresh placement state instead of copying the first chest’s variable literally.
  4. Place the second chest. Choose another key and reward. Opening chest A must not open chest B.
  5. Open RPGCode and customise. Add a special effect. A later library update must not erase that hand edit or pretend stale form controls still describe every line.

🏗️ Winston: Giving a reward and remembering “opened” needs an interruption/save policy. Two statements alone do not guarantee atomicity.

🎨 Sally: Create something once. Reuse it easily. Customise it safely.

Future verification, not a claimed test pass

These are paper scenarios. Run them through the actual game and selected plugins once supported. A simulated outcome can preview branches, but cannot count as executing a battle, validating reward persistence or testing a real save/reload.

The thread running through the evening

“we should make the often things simple one click items”

Jensen’s direction: beginner-friendly workflows and complete editing capabilities. Ordinary actions should be easy to author, with real RPGCode and reusable artwork still available underneath.
